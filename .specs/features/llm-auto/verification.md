## Findings

None of these is blocking. None contradicts an acceptance criterion or a one-way door.

1. **Fixed in round 2 (`7846377`, C18).** A retry with no dictation now runs the rules only (`OutputMode::RulesOnly`). The coordinator corrected my premise: a failed-ASR row has empty raw text, so `dictation_for` returns `None` and the app could not be stored whatever `actions.rs` passed. Original text: **Non-blocking - the retry of a failed transcription has no app, so it can call the LLM for text dictated into a disabled app.** When ASR fails, the row is saved unlinked with `app: Default::default()` (`apps/desktop/src/actions.rs:966`, behaviour from before this diff). On retry, `entry.dictation` is `None`, so `OutputMode::Auto(AppContext { app_name: None })` (`apps/desktop/src/commands/history.rs:101-103`), and D4 keeps the LLM on for an unknown app. A dictation released over `keepassxc` that first failed in ASR would go to Gemini on retry. The retry only updates the history and pastes nothing, and it is a user action. Still, the "off in sensitive apps" rule of ADR-0004 does not hold on this path. `app_context` is in scope at `actions.rs:966`, but an unlinked row has no column to keep it in.
2. **Fixed in round 2 (`637b471`; manual step in C16).** `reset_binding` sends an empty default to `clear_binding`, and `change_binding`/`restore_registration` skip an unset binding (see `## Round 2 - scoped`). It has no unit test because it needs an `AppHandle`. Original text: **Non-blocking - "reset" on the legacy shortcut can no longer clear it.** `reset_binding` calls `change_binding(id, default_binding)` (`apps/desktop/src/shortcut/mod.rs:226-229`). For `transcribe_with_post_process` the default is now `""`, and `change_binding` rejects empty input (`shortcut/mod.rs:118-120`, `"Binding cannot be empty"`). The reset button on the post-processing page (`src/components/settings/post-processing/PostProcessingSettings.tsx:433-434` via `GlobalShortcutInput.tsx:295` / `FalaKeysShortcutInput.tsx:343`) only logs `console.error` (`src/stores/settingsStore.ts:444-445`). After someone gives the legacy binding a key, the UI cannot return it to "unbound". Turning post-processing off unregisters it, but the key stays stored. Also, the first `change_binding` from an empty binding logs `error!("change_binding error: Failed to unregister shortcut...")` (`shortcut/mod.rs:169-172`) for an expected case.
3. **Non-blocking - no "working" overlay while the automatic LLM runs.** The processing overlay is shown only when `post_process` (legacy) is set (`apps/desktop/src/actions.rs:840-847`). On `transcribe`, the up to 2 s Gemini wait happens behind the "transcribing" pill. This is not an AC. Worth looking at in C16 together with the latency `TODO(windows)`.
4. **Fixed in round 2 (`7846377`).** `ARCHITECTURE.md:35` now lists `postproc` ("regras e Gemini automático no ditado do `transcribe`"), in the same commit that adds the dependency. Original text: **Non-blocking - `ARCHITECTURE.md` is now stale.** `ARCHITECTURE.md:35` says the desktop uses `core`, `secrets`, `storage` and `inject`, but `apps/desktop/Cargo.toml:55-56` now also depends on `fala-postproc`. No crate was created or renamed, so the Code Map rule does not strictly apply. The status paragraph is still out of date, and under AGENTS.md (ARCHITECTURE > AGENTS) the losing document is fixed in the same change.
5. **Non-blocking, tracked - ADR-0004's ">2 s: insert the raw text and offer 'apply edit'" is only partly met.** After 2 s the rules text is pasted (local only), and the `LateEdit` is dropped when `format` returns (`apps/desktop/src/llm_auto.rs:51-57`). The background thread finishes on its own late deadline (`crates/postproc/src/lib.rs:228-230`). The plan places "apply edit" in F7b (`feat/llm-late-edit`), so this is scope, not a defect. F7b must deliver it.

6. **New in round 2, non-blocking - the plan has two acceptance criteria numbered 8.** The new retry criterion is `8.` under S1 (`.specs/features/llm-auto/plan.md:75`), and the existing store-defaults criterion is still `8.` under S2 (`plan.md:83`). In `checks.md`, both C18 (`:35`) and C8 (`:40`) cite "AC 8", so a reference to AC 8 is ambiguous. It is a spec-numbering issue only: both criteria are proven (C18, C8).
